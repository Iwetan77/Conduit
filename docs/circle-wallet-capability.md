## What else was established

- **The endpoint is `POST /v1/w3s/user/wallets`**, body `{idempotencyKey, blockchains, accountType?, metadata?}`.
- **It returns a `challengeId`, not a wallet** (2 issued here). Creation completes in the browser, on the user's device — there is no server-side completion, and an unexecuted challenge creates nothing.
- **The blockchain identifier is `ARC-TESTNET`**, read back from `ListWallets` — the same string the API server already sends to `/user/initialize`.
- **Arc supports both account types**: `SCA` and `EOA` were both created on this user. Account type is fixed at creation, so this is a decision to take once per wallet, not later.
- **Naming survives into `ListWallets`** (`87b2ba14-3f25-52f0-a82e-e6bb2dd1774b` name `Conduit SCA probe`, refId `conduit-sca-probe`), so the business wallet is distinguishable from the personal one without keeping a mapping of our own. Worth having, but not worth trusting: the server should still record the wallet id it provisioned.
- **Wallet order in `ListWallets` is not stable.** The newest wallet came back first here. Nothing may identify a wallet by position.
- **Two wallets on one chain in a single request is rejected** (`400`, code `156017`: The specified blockchain parameters are incorrect.). One request per wallet.
- **`/user/initialize` is one-shot** — a second call answers `409` code `155106`: The user had already been initialized.. So a wallet cannot be folded into the initialize challenge for an existing user; first login is initialize, and every wallet after it is `/user/wallets`.
- **An SSO user's token cannot be minted from the API key.** `POST /v1/w3s/users/token` answers `code 2, API parameter invalid` for a user whose `authMode` is `SSO` — which every Conduit merchant is, since they sign in with Google. The server therefore cannot act on a merchant's Circle wallets on its own; it needs the user token the browser holds. That is why provisioning takes `X-Circle-User-Token` rather than being a background job.
